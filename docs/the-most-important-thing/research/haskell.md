# Notes on Haskell, Formal Systems, Type Names, and Kontrakt

## Status

This is an incomplete working draft.

It records the current position while reading Haskell-related material on formal systems, presentation, representation,
interpretation, substitution, types, and combinatory logic.

It should not be read as a final judgment.

The document will be extended as the reading continues.

---

## 1. Initial Position

Haskell-related theory should be treated primarily as mathematics.

It should not be treated as engineering authority.

Kontrakt may use a very small subset of Haskell-related ideas as mathematical tools.

Even that subset must be rewritten, restricted, and lowered into machine-realistic contract material before it can be
used.

The working position is not:

```text
Haskell theory is mostly acceptable if lowered.
```

The working position is:

```text
Most Haskell theory is rejected as Kontrakt engineering.

A small number of mathematical warnings and naming tools may be studied.

Anything retained must be changed to fit explicit contracts, machine boundaries, resource limits, diagnosable failure, and replaceable realization.
```

The existence of an implementation is not enough to make a theory an engineering model.

A formal system may be implementable.

That does not mean it provides a good machine architecture.

For Kontrakt, engineering authority requires:

```text
practical utility
predictable resource behavior
diagnosable failure
explicit boundaries
replaceable realization
operational stability
mechanical fit
```

---

## 2. Haskell as Mathematical Tool, Not Machine Doctrine

Haskell and combinatory logic may be useful as mathematical material for studying:

```text
formal systems
substitution
self-application
type discipline
interpretation
presentation
representation
equational reasoning
```

But these are tools for analysis.

They are not machine doctrine.

The rejected move is:

```text
formal computation model
-> direct system architecture
```

The accepted move is much narrower:

```text
formal computation model
-> limited mathematical warning
-> selected contract-naming insight
-> rewritten Kontrakt material
```

Kontrakt must not import Haskell-style expression-first computation as architecture.

Kontrakt must not treat Haskell's type theory, laziness, function values, thunks, or higher-order composition as
contract material.

---

## 3. The Main Risk: Smuggling the Machine into Pure Logic

Pure logic by itself is not the problem.

A formal system may define:

```text
atoms
terms
operations
formation rules
substitution
reduction
interpretation
```

That is acceptable as mathematics.

The problem begins when a formal explanation quietly starts to behave as if it were also a machine explanation.

For example:

```text
formal object
expression
reduction
interpretation
```

are mathematical concepts.

A machine has different obligations:

```text
memory
layout
allocation
lifetime
resource bounds
failure modes
visibility
diagnostics
publication
```

If a theory moves from formal expression to machine execution without accounting for these, it becomes dangerous.

Kontrakt should reject this drift.

Pure logic may ignore the machine.

Engineering cannot.

---

## 4. Data Is Not Merely a Process in Kontrakt

Some formal-system explanations treat objects as generated by atoms and operations.

In that setting, an object may be understood through its process of generation.

That may be acceptable inside a formal system.

Kontrakt should not adopt this as an engineering principle.

Kontrakt treats accepted immutable facts as contract material.

An implementation may compute candidate facts.

Kontrakt then judges whether those candidates can become accepted material.

The accepted model is:

```text
accepted facts
-> implementation realization
-> candidate facts / candidate transition
-> Kontrakt judgment
-> accepted facts / accepted transition / declared failure
```

The rejected model is:

```text
expression / generation process / thunk
= contract material
```

A computation process may produce a candidate.

It does not own contract truth.

---

## 5. Lazy Evaluation and Thunks Are Not Contract Material

Haskell may delay evaluation.

A value may be represented by a thunk until it is demanded.

This does not mean that Haskell literally erases data.

But it does mean that runtime representation may hold a deferred computation instead of an already materialized value.

For Kontrakt, this is not an acceptable contract material model.

The contract machine should not make closure chains, thunks, or delayed reduction paths the carrier of contract
authority.

The contract authority should remain in:

```text
accepted immutable facts
declared boundaries
declared transitions
declared failures
publication judgments
```

A thunk may be a runtime implementation detail in some language.

It must not become Kontrakt contract material.

---

## 6. Substitution as a Mathematical Warning

Substitution is useful as a mathematical warning.

It shows what happens when a variable or symbol is replaced by another expression.

Unrestricted substitution is dangerous.

Self-application examples show why a system needs type, domain, or formation discipline.

The useful lesson is narrow:

```text
not every expression may be substituted into every position
```

Kontrakt can reinterpret this as an admission rule.

A contract surface must define what may enter a position.

A contract name, input fact, operation argument, transition event, or state must have an admissibility rule.

The rejected model is:

```text
anything can be applied to anything
```

The accepted Kontrakt model is:

```text
only admitted material may enter declared contract positions
```

This is not an adoption of Haskell's computation model.

It is only a warning about uncontrolled substitution.

---

## 7. Interpretation

Interpretation is useful, but it must be kept at the mathematical level unless it is explicitly lowered.

In a formal system, interpretation gives meaning to symbols, expressions, types, or operations.

It maps a presentation into a semantic domain.

For example:

```text
symbol / expression / type
-> meaning
```

For Kontrakt, the analogous structure is:

```text
contract presentation
-> interpreted contract meaning
```

However, interpretation alone is not engineering.

Kontrakt must still ask:

```text
Was the interpretation acquired into canonical material?
Was the representation chosen correctly?
Was the realization checked?
Was the output accepted by judgment?
Was failure diagnosable?
```

Therefore:

```text
interpretation reads meaning
verification checks preservation
realization computes candidates
Kontrakt judges acceptance
```

Haskell's interpretation concepts may help describe meaning assignment.

They are not sufficient for machine governance.
---

## 8. Formal Truth, Interpretation Validity, and Engineering Validity

A formal theorem may remain true inside its own formal system.

That does not give engineering authority to its interpretation.

The useful distinction is:

```text
Formal truth:
    whether a theorem follows from the rules of the formal system

Interpretation validity:
    whether the formal system has been correctly mapped to a subject matter

Engineering validity:
    whether that interpretation survives the machine:
    cost, memory, failure, observability, determinism, diagnosability,
    resource bounds, and replaceable realization
```

The dangerous move is:

```text
the theorem remains formally true
-> therefore the applied model is acceptable
```

Kontrakt rejects that move.

If a formal system is applied to software and its interpretation fails on the machine, then the applied model has failed
for engineering purposes.

The theorem may remain mathematically true.

The engineering interpretation has failed.

Kontrakt must not allow a theory to escape back into formal truth after its software interpretation fails.

For Kontrakt, an applied formal model must survive:

```text
explicit boundary control
accepted immutable facts
legal transitions
bounded resources
diagnosable failure
stable identity
observable lifecycle
controlled publication
replaceable realization
```

If it does not survive those conditions, it is not acceptable as Kontrakt engineering material.

Working rule:

```text
Formal truth is not engineering authority.

A failed machine interpretation is an engineering failure,
even if the formal theorem remains true.
```

## 9. Contract, Contract Presentation, and Type Name

The important reinterpretation is this:

```text
type is not merely a category
type is the name of a contract presentation
```

A contract is abstract.

A contract presentation is the software-visible document of that contract.

A type is the visible name of that contract presentation.

The working distinction is:

```text
Contract:
    abstract obligation or meaning

Contract Presentation:
    software-visible document of that contract

Type:
    visible name of a contract presentation

Canonical Contract Material:
    authority after acquisition and lowering
```

The type is not a pointer to the contract.

It does not point to a memory location or object.

It is closer to the title of a contract document.

It says under which contract presentation a value, fact, material, operation, or state claims to be governed.

The type name is not full contract authority.

The authority remains in canonical contract material.

---

## 10. Type as Contract-Document Name

Traditional theory often treats a type as a category of values.

Kontrakt should treat a type as the name of a contract document.

For example:

```text
RawCustomerId
CanonicalCustomerId
AdmittedOrderCommand
FrozenContractMaterial
PublishedResult
```

These are not merely value categories.

They are names of different contract presentations or contract states.

Each name says:

```text
this material claims to be governed by this contract document
```

For example:

```text
CanonicalCustomerId
```

should be read as:

```text
the software-visible name of the Canonical Customer Identity contract presentation
```

not merely as:

```text
a subtype or category of String
```

This matters because the contract document may include:

```text
canonicalization rule
stable identity rule
acquisition-order independence
diagnostic preservation
equality law
ordering law
lowering rule
```

The type name is useful because it gives the contract document a visible name in software.

But the type name alone is not enough.

It must be acquired and lowered into canonical contract material.

## 11. Haskell Types as Extremely Limited Mathematical Tools

If types are understood as contract-presentation names, then a small part of Haskell's type-centered reasoning may be
useful as mathematics.

Possible limited uses:

```text
type signature:
    a visible claim that an expression belongs under a named contract presentation

type constructor:
    a mathematical way to discuss construction of contract names or presentations

type variable:
    an unspecified contract position

algebraic data type:
    a closed set of named contract cases

newtype:
    a way to give a different contract-document name to a similar representation

type class:
    a possible mathematical analogy for an operation-contract family
```

These are only analogies and tools.

They are not accepted as Kontrakt engineering.

Kontrakt must not inherit Haskell's function-value assumptions, lazy evaluation assumptions, or expression-first
architecture from these ideas.

Anything retained must be rewritten into explicit Kontrakt terms such as:

```text
contract presentation
contract name
contract clause
fact id
operation id
transition id
predicate id
policy rule id
failure id
canonical contract material
```

## 12. Representation Is Not Contract Authority, But It Matters

A common mathematical move is to say that different representations may denote the same abstract object.

Inside pure formal reasoning, this may be acceptable.

On a machine, representation is physically consequential.

Representation affects:

```text
cost
allocation
failure behavior
determinism
observability
diagnosability
identity
ordering
publication safety
```

Therefore, Kontrakt must not say:

```text
representation does not matter
```

The correct position is:

```text
representation must not define the contract
but representation must preserve the contract
```

Representation is a replaceable realization.

But it is still a verification target.

If representation can change identity, ordering, equality, failure mode, visibility, or publication safety, then its
relevant constraints must be promoted into contract material.

---

## 13. Representation Conditions Can Become Contract

Not all representation details are contract.

These may remain implementation details:

```text
temporary buffer
helper function
local cache
internal loop shape
private data structure choice
```

But representation conditions become contract when changing them would change software meaning or contract preservation.

Examples:

```text
canonical encoding
stable identity
equality law
ordering law
nullability / absence rule
precision / rounding rule
serialization schema
wire format
memory ownership
mutability rule
publication visibility
lifetime
resource envelope
```

These are not merely physical details when downstream contracts depend on them.

Working rule:

```text
representation as authority is rejected
representation preservation as contract is accepted
```

## 14. What Must Be Rejected

Kontrakt should not import the following as contract architecture:

```text
function values as contract material
closures as contract flow
thunks as accepted facts
lazy reduction chains as machine lifecycle
higher-order function composition as system topology
recursive reduction as runtime structure
type-level tricks as contract authority
expression-first computation as contract machine
```

These may exist in a host language.

They must not own contract meaning.

If they appear in an authoring surface, they must be rejected, ignored, or rewritten into explicit contract material
before becoming authoritative.

Surviving forms should be:

```text
contract name
contract presentation
contract term
fact id
operation id
predicate id
transition id
policy rule id
failure id
```

not function values, thunks, or closures.

## 15. Mathematical Use Without Engineering Authority

The current working position is:

```text
Haskell theory may be used only as mathematics.

Only a very small subset may be useful.

Even that subset must be changed to fit Kontrakt.

It should not be granted engineering authority merely because it is implemented.
```

Machine fit means at least:

```text
explicit boundaries
predictable cost
bounded resources
diagnosable failure
replaceable realization
stable identity
observable lifecycle
controlled publication
```

Kontrakt should not accept Haskell-style purity, laziness, expression reduction, or type-level elegance as proof of
engineering validity.

---

## 16. Where the Tension Appears

The tension appears when Haskell-like explanations move between three levels without enough separation:

```text
Mathematical Level:
    formal objects, expressions, reduction, interpretation

Language Level:
    types, syntax, functions, laziness, evaluation strategy

Machine Level:
    runtime representation, allocation, thunks, closures, memory, failure
```

The mathematical level may be useful.

The language level may be instructive.

The machine level must be judged by engineering criteria.

The problem is the forced slide:

```text
mathematical elegance
-> language feature
-> machine principle
```

Kontrakt should not accept that slide.

Each level must be separated and explicitly lowered.

---

## 17. Current Working Rule

The current working rule is:

```text
Do not treat Haskell theory as engineering authority.

Do not confuse formal truth with engineering validity.

Do not imply that most Haskell theory can be accepted by lowering.

Use only a very small subset as mathematical warning or naming aid.

Do not import expression-first computation as contract architecture.

Do not treat representation as irrelevant on the machine.

Do not treat type as mere category.

Treat type as the name of a contract presentation.

Treat interpretation as meaning assignment, not runtime governance.

Rewrite any retained idea into explicit Kontrakt contract material before considering it useful.
```
